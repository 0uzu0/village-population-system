普通用户默认被授予全部业务权限，含批量导入 P0 已确认跳过

backend/src/db/migrations/V002__seed_data.sql:47-51
问题
授权模型是「黑名单」：SELECT 2,id FROM sys_permission WHERE code NOT IN (user:*, system:*, audit:view)。除删除人员外，普通用户拥有一切——包括 excel:import（批量写入）、tag:manage（改他人标签）、person:export（导出全库含身份证号）。

bcrypt 同步 API 阻塞事件循环 P0 未采用（实测无收益）

backend/src/utils/crypto.ts:5,9 · 调用点：auth.ts 登录/改密、user.ts 建号改密
问题
bcrypt.hashSync / compareSync 在 cost=10 下单次约 60–100ms，期间整个 Node 进程停摆。本项目是单容器单进程部署，没有多副本分担。
影响
早晨集中上班时 20 人同时登录 → 串行阻塞约 1.6 秒，期间所有人的请求（包括正在拍照上传的现场作业）全部排队。这恰好是村务系统最典型的使用峰值。登录限流按 IP 计，挡不住这种「正常并发」。
建议
改用 bcrypt.hash() / bcrypt.compare()（Promise 版），把 crypto.ts 的两个函数改成 async，同步调整 4 处调用点（都是 async 路由，改动局部）。顺带把 cost 提到 12（异步后单次耗时不再影响吞吐，可以换更强哈希）。
代价
30 分钟。注意 verifyPassword 在登录失败分支里被调用，签名变更要一并改。
复核
本条建议经实测后未采用。bcryptjs 的异步实现按 MAX_EXECUTION_TIME = 100ms 切片、每片之间用 nextTick 让出，而 cost=10 单次 hash 实测约 90ms、compare 约 74ms——不到 100ms 就不会让出，整段仍是同步跑完。实测 async 版 cost=10 总耗时 82ms、期间事件循环只 tick 了 1 次，与同步版无差别。要让分片真正生效必须把 cost 提到 11–12（实测 148–326ms），但那会让每次登录更慢，在「数人使用、登录并发极低」的场景下得不偿失。结论：改 async 是假修复，保持 hashSync/compareSync + cost=10。若将来换用原生 bcrypt（C++ 绑定，跑在线程池）或改用 argon2，此条应重开。

缺少安全响应头 + CORS 配置自相矛盾 P0 已修 v2.2.0

backend/src/app.ts:28-30（无 helmet）· cors({origin: … , credentials: true})
问题
① 未引入 helmet，全局缺 X-Frame-Options、X-Content-Type-Options、Referrer-Policy（只有 file.ts:457 对单个响应设了 nosniff）；② CORS_ORIGIN 默认 '*' 时代码走 origin: true（反射任意来源）却同时开了 credentials: true。

JWT 无撤销机制，改密码后旧 token 仍有效 7 天 P1 已修 v2.2.0

backend/src/middleware/auth.ts:14-17（payload 仅 uid/username）· auth.ts:76 改密不失效
问题
token 签名里不含任何「凭据版本」。停用账号靠每次请求查 active 挡住了，但改密码不会让已签发的 token 失效。有效期刚从 12h 延长到 7d，这个窗口也放大了 14 倍。
影响
手机丢失后改密码，捡到手机的人仍能继续使用整整 7 天（离线队列还会继续往服务端写数据）。这是延长有效期带来的直接副作用，需要配套机制。
建议
在 sys_user 加 token_version INT DEFAULT 0，signToken 时写入 payload，authMiddleware 里与缓存中的用户版本比对，不一致即 401；改密码 / 停用 / 重置密码时 token_version + 1 并失效缓存。App 与 PC 都已有统一的 401 处理，无需改客户端。
代价
2 小时（含一个迁移、一次 loadAuthContext 的字段扩展、2 条单测）。

v2.2.0 实际改动与审计建议的偏差

  • bcrypt 改异步未采用（保持同步 + cost=10）。实测 bcryptjs 的异步版本按 MAX_EXECUTION_TIME = 100ms 切片让出，而 cost=10 单次 hash 只需约 90ms、compare 约 74ms，整段根本不会让出事件循环——改 async 只多出一层 Promise，收益为零。真要分片生效须把 cost 提到 11–12（单次 148–326ms），但那样每次登录都更慢，而本项目登录并发极低。结论：改 async 是个假修复，不做。
  • helmet 关掉了 CSP 与 HSTS。CSP 作用于 HTML 文档，而本服务只返 JSON 和附件字节（页面由 nginx 提供）；HSTS 会把「局域网 HTTP 部署」直接锁在门外。只开其余默认项即可。
  • 上传上限刻意留在后端 multer，nginx 的 client_max_body_size 保持 0。multer 是流式落盘，超限立即中止并删临时文件，且能返回带数值的中文提示；nginx 的 413 只会吐 HTML 错误页，前端 axios 取不到 message。
  • 互斥口径用「数据驱动」而非「编码判断」。tag_definition 新增 exclusive_group / exclusive_priority，HUKOU_POP=10、FLOATING_POP=20 同组，因此仍保持「户籍优先」，但代码里不再出现这两个编码。读侧（统计/标签人数/列表筛选）与写侧（建档/编辑/单加/批量/两条 Excel 导入/存量迁移）全部读同一份数据，此前「工作台数字 ≠ 标签页数字」的口径分裂随之消除。

07不需要改的地方

  • 不要为了「分层」而引入 Prisma / TypeORM / NestJS。现在的 mysql2 + 手写参数化 SQL 在 77 个路由规模下完全够用，且 SQL 可读、EXPLAIN 方便。ORM 会带来「查出来的 SQL 不可控」这个新问题，而本项目没有跨库/多方言需求。
  • 不要给所有接口加限流。只有登录需要——业务接口都要求鉴权，且网格员批量上传照片是正常行为，限流会伤真实用户。真要防刷，先做「同一 token 的文件上传并发上限」。
  • 不要把 token 从 localStorage 搬到 httpOnly cookie。看似更安全，但 APP 端要改 OkHttp 拦截器、PC 要处理 CSRF，投入产出比很差。真正该做的是保持「无 v-html」这条纪律（当前全项目 0 处，很好）并补 CSP。
  • 不要重写 Android 的离线队列。OfflineQueue + SyncEngine 的分层（纯逻辑可测、失败分可恢复/不可恢复、网络中断即中止整轮省电）比多数商业 App 做得细，只在上面补乐观锁冲突识别即可。
