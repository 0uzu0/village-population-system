# 项目优化建议（纵览版）

> 评审范围：`backend/src`（34 个 TS 文件 / 6169 行）、`frontend/src`（34 个文件 / 6281 行）、
> 迁移脚本 V001–V013、CI 流水线、Docker 部署编排。
> 结论：**架构方向是对的**（手写 SQL + zod 校验 + 配置即代码 + 迁移可重入），
> 主要问题集中在「单文件过大」「口径重复」「测试类型单一」「性能靠子查询」四类。

---

## 0. 现状体检

| 维度 | 现状 | 评价 |
|---|---|---|
| 后端分层 | `modules`（路由+业务+SQL 同一文件）+ `utils`（纯函数）+ `middleware` | 目录清晰，但模块内无分层 |
| 最大单文件 | `modules/excel.ts` **1484 行**（占后端 24%） | ⚠️ 已是巨石 |
| 前端页面 | `person/index.vue` **770 行**、`keygroup` 639、`excel` 584 | ⚠️ 单页过大 |
| 后端测试 | 21 个测试文件 / 202 例 | ⚠️ **几乎全是「读源码字符串断言」**，非运行时测试 |
| 前端测试 | **无**（仅 `check:icons` 静态检查） | ❌ 空白 |
| 代码规范 | **无 ESLint / Prettier** | ❌ 空白 |
| 校验一致性 | 36 处已改 `.nullable().optional()`，**仍有 40+ 处** `.optional().or(z.literal(''))` | ⚠️ 同类坑未清完 |
| 性能热点 | 每请求 3 次权限查询；统计靠 N×6 相关子查询 | ⚠️ 有优化空间 |
| 部署 | CI 双段流水线 + 健康检查 + 资源限额 + 内部网络隔离 | ✅ 做得不错 |

## 一、模块化

### 1.1 后端：`excel.ts` 必须拆（P1，最高杠杆）

1484 行里混了四类互不相干的职责：

| 职责 | 行号区间 | 建议去处 |
|---|---|---|
| 模板生成（普通/重点人群/专项） | 170–240、887–943 | `excel/template.ts` |
| 人口档案导入 | 241–700 | `excel/importPerson.ts` |
| 重点人群名单打标签导入 | 700–875 | `excel/importKeyGroup.ts` |
| 专项台账导入（残疾/特困/低保） | 944–1201 | `excel/importSpecial.ts` |
| 导入任务状态机 + 错误明细 | 402–630、1202–1232 | `excel/importTask.ts` |
| 导出 | 1325–1483 | `excel/export.ts` |

拆法不必激进——**先按上表拆成同目录多文件、共用一份 `readRowsByColumns` 与 `SPECS` 配置**，
`modules/excel.ts` 保留为路由聚合入口（`router.use` 各子路由）。改动是机械搬迁，风险低，
但能让后续加「第 4 类专项台账」只碰一个文件。

### 1.2 后端：模块间横向依赖应下沉到 service

`modules/statistics.ts` 顶部 `import { markStaleImportTasks } from './excel'` ——
统计模块直接依赖导入模块的内部函数，等于把两个模块焊死。建议：

```
src/services/importTask.ts   ← markStaleImportTasks / markImportFailed
src/modules/excel.ts         ← 只做路由，调用 service
src/modules/statistics.ts    ← 调用 service
```

同理，`keygroup.ts` 里 `QUICK_GROUPS`、`focusTagSelects`（`grid.ts`）、
统计模块里的标签口径，**三处各写一遍人群定义**，应统一到一个 `utils/focusGroups.ts`，
被 统计 / 重点人群 / 导出 / 网格 共同引用（现在改动一个人群要在 3–4 个文件同步）。

### 1.3 前端：抽列表页 composable（P1）

`person / keygroup / excel / tag / pending / family / grid` 七个列表页重复同一套样板：
`loading` + `load()` + `doSearch()` + `resetQuery()` + `syncUrl()` + `restoreQuery()` +
分页 + 列显隐（`isColVisible` / `toggleColumn` / `restoreColumns`）。

建议提 `composables/`：

```
useListQuery.ts        // 查询对象 + syncUrl/restoreQuery + doSearch/resetQuery
useColumnVisibility.ts // 列显隐 + localStorage 持久化
useTableSelection.ts   // 批量选中 + 批量操作入口
```

以 `person/index.vue`（770 行）为例，这三块约占 150–200 行，抽走后主页面能降到 550 行上下，
且新列表页直接复用，不再复制粘贴。

### 1.4 前端：`any` 泛滥，缺 DTO 类型

`api/index.ts` 的方法返回 `Promise<ApiResult<T>>`，但视图里普遍 `ref<any>({})`，
后端字段名一改（历史上发生过驼峰/下划线事故两次）编译期完全不报错。
建议在 `types/api.ts` 里为 `PersonVO`、`KeyGroupFilter`、`LedgerRecord` 等定义接口，
`api/index.ts` 全部显式泛型化。这是**把已有事故变成编译期错误**的投入。

## 二、性能

### 2.1 每请求 3 次权限查询（P0，最快见效）

`middleware/auth.ts` 的 `loadAuthContext()` 每个请求都要查
`sys_user` + `sys_role` + `sys_permission` 三条 SQL。万级人口场景下 QPS 不高，
但**每个 API 调用（含列表翻页、图表轮询）都白付 3 次往返**。

方案（任选）：
- **内存 TTL 缓存**：`Map<userId, {ctx, expireAt}>`，TTL 60s，改角色/权限时主动失效；
- 或把 `permissions` 直接写进 JWT claim（代价：改权限要重新登录）。

推荐前者，改动约 30 行，收益立竿见影。

### 2.2 统计靠「相关子查询 × N」（P1）

`grid.ts` 的 `focusTagSelects()` 为每行生成 **6 个相关子查询**：

```sql
(SELECT COUNT(DISTINCT pt.person_id) FROM person_tag pt JOIN ... WHERE ... ) AS party_count,
(SELECT COUNT(DISTINCT pt.person_id) FROM ...) AS disabled_count,
... × 6
```

村庄列表有 N 个村庄 → **6N 次 person_tag 扫描**；网格列表同理。
建议改为**一次 JOIN + 条件聚合**：

```sql
SELECT p.village,
  COUNT(DISTINCT CASE WHEN td.code IN ('PARTY_MEMBER','PARTY_PROBATIONARY') THEN p.id END) AS party_count,
  COUNT(DISTINCT CASE WHEN td.code = 'DISABLED_PERSON' THEN p.id END) AS disabled_count,
  ...
FROM person p LEFT JOIN person_tag pt ON pt.person_id = p.id AND pt.status='ACTIVE'
     LEFT JOIN tag_definition td ON td.id = pt.tag_id
WHERE ...
GROUP BY p.village
```

`statistics.ts` 的 `/dashboard`（5 个大 COALESCE 子查询 + 2 组 IN 列表子查询）同理。
若统计页访问频繁，可进一步加**统计快照表**（定时任务或写操作后失效标记）。

### 2.3 深分页与索引

- `LIMIT ? OFFSET ?` 在万级无感，十万级会退化 → 届时改 keyset 分页（按 `id > ?`）。
- 索引 V006 已补得很到位（`idx_pt_person_tag_status`、`idx_person_village_status` 等）。
  建议：对 `family_member` 的 `person_id`、`ledger_record(category, record_date)`
  做一次 `EXPLAIN` 基线核查，把未覆盖的筛选组合补上。
- **建立 EXPLAIN 基线脚本**：把 5 个最重查询的 `EXPLAIN` 输出写成测试断言，
  防止后续加 JOIN 时悄悄退化成全表扫。

### 2.4 前端打包体积（P1）

- **echarts 现为全量引入**（`import * as echarts`）。改为按需：
  `import { BarChart, PieChart, LineChart } from 'echarts/charts'` +
  `use([...])`，包体积可从 ~1MB 降到 ~300KB。
- **Element Plus 全量注册**。若构建产物 `vendor` 超过 800KB，
  建议上 `unplugin-vue-components` 按需导入。
- 所有路由已是 `() => import()` 懒加载 ✅。建议在 CI 里加一步
  `vite build` 后输出 gzip 体积报告，超阈值告警。

## 三、可维护性

### 3.1 🚨 测试类型单一：全是静态断言

21 个测试文件绝大多数是「读源文件字符串，断言包含某片段」
（`expect(src).toContain(...)`）。这类测试：
- ✅ 能防止「有人悄悄改回旧写法」（如把 20MB 上限加回来），有价值；
- ❌ **发现不了任何运行时缺陷**——SQL 语法错、字段名拼错、事务没回滚、导入丢数据，
  一个都测不出来。

建议补一层**集成测试**：用 `docker compose` 起一个 MySQL（或 testcontainers），
对关键链路做真库测试：
1. 导入 → 落库 → 详情/列表/统计口径一致；
2. 人员删除的级联（`person_tag`/`family_member`/`person_change_log`/`person_disability`）；
3. 重点人群筛选 → 导出 口径一致（历史上错过两次）；
4. 村庄联系人 upsert → 两字段皆空删行。

### 3.2 🚨 zod 可空字段模式不统一

项目已踩过坑并修了 36 处，但**仍有 40+ 处**在用
`.optional().or(z.literal(''))`——这个联合类型**拒绝 `null`**，
一旦某个编辑接口把详情里的 `null` 回显提交上来，就是 500 `Invalid input`。
当前靠「前端用 `|| ''` 兜底」侥幸没炸（如 `grid/index.vue` 的 `openEdit`）。

建议：全量替换为 `.nullable().optional()`（或抽一个
`const optionalStr = (max: number) => z.string().max(max).nullable().optional()` 统一封装），
并加一条静态测试**断言源码中不再出现 `.or(z.literal(''))`**，把坑彻底封死。

### 3.3 「在册」口径硬编码 8 处

`PERSON_ACTIVE_SQL = "p.status IN ('NORMAL','MOVED_IN')"` 只对别名 `p` 有效，
其余 7 处（`grid.ts` ×4、`keygroup.ts` ×2 等）各自手写字符串。历史上多次出现
「新增统计忘加在册过滤 → 死者仍出现」。

建议改成 `activeSql(alias = 'p')` 返回带别名的片段，全项目只此一处定义。

### 3.4 死代码与安全

| 位置 | 问题 | 处置 |
|---|---|---|
| `grid.ts:256` `transfer-person` | `buildGridFilter()` 结果与 `inClause` **算了但没用** | 要么删，要么真正用于数据范围校验 |
| `rbac.ts:36` `buildGridFilter()` | 恒返回空 = **所有人可见全部数据** | 这是「网格员只看本网格」的预留插口，注意当前语义 |
| `env.ts:40,44` | `JWT_SECRET` / `ADMIN_INIT_PASSWORD` 有可用的**弱默认值** | 生产启动时校验：非 dev 环境禁止使用默认值，否则拒绝启动 |
| `middleware/auth.ts` | 登录**无限流** | 加 `express-rate-limit`（如 5 次/分钟/IP） |
| `file.ts` | 类型白名单只校验**扩展名**（可伪造） | 增加 magic number（文件头）校验，或至少校验 MIME+扩展名一致 |
| `utils/async-shim.ts` | 猴补丁 express 内部 `Layer.prototype` | 脆，升级 Express 5 或改用显式 `asyncHandler(fn)` 包装 |

### 3.5 规范与注释

- **补 ESLint + Prettier**，CI 加 `lint` 步骤（现在风格全靠自觉）。
- 过期注释：`V001` 里 `person.status` 仍写 `'NORMAL/MOVED_IN/MOVED_OUT/CANCELLED'`，
  但 `CANCELLED` 已在 V007 废弃——新迁移里说明即可，避免误导。
- `docs/` 已有 4 篇文档，建议把「口径定义」（在册、重点人群、条口）单独抽一篇
  `口径说明.md`，作为业务与技术共同的唯一事实来源。

## 四、后续功能拓展

### 4.1 数据范围（多网格/多村权限）——最大的预留能力

`buildGridFilter()` 现在是空实现，即「所有人看全部数据」。**插口已在、开关未开**。
要做「网格员只管理本网格」时：
1. 恢复 `sys_user.grid_scope`（或角色维度）配置；
2. `buildGridFilter` 按登录用户生成 `AND p.grid_id IN (...)`；
3. 校验所有 `buildGridFilter` 调用点确实接入了 WHERE；
4. 前端筛选器下拉按范围收敛。

这是**当前架构留得最好的一个扩展点**，值得优先规划。

### 4.2 附件能力已通用，可直接复用

`file_info.biz_type / biz_id` 是通用挂载设计，目前只有台账在用。
后续可低成本把合同/证明材料挂到 **人员档案、家庭、网格、议题**，
零后端改动（前端复用 `AttachmentUploader.vue`）。

### 4.3 配置迁移：条口字典化

`utils/ledger.ts` 的 `LEDGER_CATEGORIES` 是 config-in-code。
**规则**：条口 ≤ ~8 个时保持代码内配置最省事；**继续增长到 10+ 或需要业务方自助维护时**，
应迁移为字典表 + 管理页（`ledger_category` / `ledger_work_type`），
否则每加一个条口都要发一次版本。可参考 `tag_definition` 的既有模式。

### 4.4 移动端采集（若网格员需入户）

当前是纯 PC 后台。若一线网格员要入户采集，建议：
- **复用同一套后端 API**（已 RESTful、Bearer 鉴权、无 Cookie 依赖，天然适配移动端）；
- 单独做一个轻量 H5 / 小程序端，只保留「人员查询、状态变更、打标签、上传照片」；
- 后端需补：图片压缩上传、离线草稿同步接口、弱网重试。

### 4.5 数据质量与智能

- **重复人员识别**：同身份证多档案、同名同村疑似重复 → 定期跑批出报告；
- **标签规则引擎**：按年龄/残疾等级/供养方式自动打标签（现在部分靠导入时写死）；
- **数据完整性看板**：身份证缺失、手机号缺失、无网格、无家庭 的欠账清单；
- 这三项都能复用现有 `import_pending` + `audit_log` 骨架。

### 4.6 可观测性

- 现在只有容器 `json-file` 日志 + `/api/health`。建议加：
  - **结构化日志**（pino）+ 请求 ID 贯穿；
  - **慢 SQL 日志**（>200ms 打印 SQL 与参数）；
  - 关键指标（导入耗时、导出耗时、登录失败数）落到一张 `ops_metric` 表，
    工作台上做一个「系统健康」卡片。

## 六、一句话总结

架构骨架（迁移可重入、配置即代码、纯函数工具层、统一响应）是健康的，
**当前最该做的三件事**：
1. **拆 `excel.ts`**（模块化最大瓶颈）；
2. **把 zod 可空字段统一 + 补真库集成测试**（维护性最大隐患）；
3. **权限上下文缓存 + 统计改 JOIN**（性能最直接收益）。

功能拓展方面，`buildGridFilter` 的数据范围插口、通用附件表、以及
「同后端 API 供移动端」三条路都已铺好，属于**低成本高上限**的方向。
