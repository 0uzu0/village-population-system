# 村级人口与重点人群精细化管理系统 —— 部署文档

> 目标读者：不要求精通 Docker 的运维人员。按本文档步骤即可完成从代码到上线的全过程。

本系统采用前后端分离 + 模块化单体后端架构：

- **前端**：Vue 3 + TypeScript + Vite + Element Plus，构建为静态文件，由 Nginx 提供并反向代理 API。
- **后端**：Node.js + Express + MySQL（模块化单体）。
- **部署**：Docker + Docker Compose，镜像发布到 GitHub Container Registry（GHCR）。

---

## A. GitHub 配置

### 1. 创建 GitHub 仓库

在 GitHub 新建仓库（建议私有仓库，因为包含业务代码），例如 `your-org/village-population`。

### 2. 推送项目代码

```bash
git init
git add .
git commit -m "init: 村级人口管理系统"
git branch -M main
git remote add origin https://github.com/your-org/village-population.git
git push -u origin main
```

> 安全提醒：`.gitignore` 已排除 `.env`、备份文件等，**切勿**将真实村民信息、密码、密钥提交到仓库。演示数据均为虚构。

### 3. 检查 Actions 权限

- 打开仓库 **Settings → Actions → General**，确保 `Workflow permissions` 中勾选 **Read and write permissions**（用于写 GHCR 包）。
- 确保 `Allow GitHub Actions to create and approve pull requests` 等选项按需开启。

### 4. 配置环境变量和 Secrets

本工作流使用 `GITHUB_TOKEN` 自动登录 GHCR，**无需**创建长期有效的 Personal Access Token，也无需额外配置 Secrets。

如镜像仓库为私有，服务器拉取镜像时需要凭证（见 A.9）。

### 5. 执行 GitHub Actions 工作流

推送代码到 `main` 分支后，工作流 `.github/workflows/docker-publish.yml` 自动触发：

1. 执行后端单元测试、类型检查与构建；
2. 执行前端构建；
3. 通过 Docker Buildx 构建 `linux/amd64` 镜像（单架构，无需 QEMU 模拟）；
4. 推送到 GHCR，生成 `latest`、`sha-<短哈希>` 标签。

推送版本标签可发布版本镜像：

```bash
git tag v1.0.0
git push origin v1.0.0
```

将生成不可变的 `v1.0.0`、`v1.0`、`v1` 标签。

手动触发：仓库 **Actions → docker-publish → Run workflow**。

### 6. 查看构建和测试日志

**Actions** 页签 → 选择对应 workflow run → 展开 `test` / `build-and-push` 步骤查看日志。测试失败会阻止发布（`build-and-push` 依赖 `test` 成功）。

### 7. 确认镜像发布到 GHCR

打开 GitHub 用户/组织主页的 **Packages** 页签，应看到：

- `ghcr.io/your-org/village-population-frontend`
- `ghcr.io/your-org/village-population-backend`

### 8. 配置镜像公开或私有访问

- 进入 Package → **Package settings → Manage Actions access** 可控制仓库的推送权限。
- 镜像默认**私有**。若服务器需要拉取，需在 A.9 配置凭证；或将镜像设为公开（`Package settings → Change visibility → Public`），公开后服务器可匿名拉取。

### 9. 私有镜像的服务器拉取凭证

如需拉取私有镜像，推荐创建**只读、最小权限**的 Personal Access Token（`read:packages` 作用域），在服务器上：

```bash
echo "YOUR_TOKEN" | docker login ghcr.io -u YOUR_GITHUB_USERNAME --password-stdin
```

> 对于同一仓库的自动发布，优先使用 `GITHUB_TOKEN`（工作流已内置），不要在 CI 中无必要地创建长期 PAT。

## B. 服务器部署

### 1. 准备 Linux 服务器

建议配置：2 核 4G 内存、40G 磁盘（满足 1 万级人口规模）。系统建议 Ubuntu 22.04/24.04 LTS。

### 2. 安装 Docker Engine 和 Docker Compose Plugin

```bash
# Docker 官方一键安装
curl -fsSL https://get.docker.com | sh
# 验证
docker --version
docker compose version
```

### 3. 创建部署目录

```bash
mkdir -p /opt/village-population && cd /opt/village-population
```

### 4. 上传部署文件

将项目 `deploy/` 目录内容上传到服务器（scp / 直接克隆仓库均可）：

```bash
# 方式一：克隆仓库后取 deploy 目录
git clone https://github.com/your-org/village-population.git
cd village-population/deploy
# 方式二：scp 上传
scp -r deploy/* user@server:/opt/village-population/
```

### 5. 配置 .env

```bash
cp .env.example .env
vim .env   # 填写 MYSQL 密码、JWT_SECRET、ADMIN_INIT_PASSWORD、镜像地址与版本
```

生成随机密钥：

```bash
openssl rand -hex 32   # 用于 JWT_SECRET
```

### 6. 登录 GHCR（私有镜像场景）

```bash
docker login ghcr.io -u YOUR_GITHUB_USERNAME
```

### 7. 拉取指定版本镜像

```bash
docker compose pull
```

### 8. 启动数据库和应用

```bash
docker compose up -d
docker compose ps
```

首次启动流程：MySQL 建库 → 后端自动执行数据库迁移 → 自动创建初始管理员账号（`.env` 中 `ADMIN_INIT_USERNAME` / `ADMIN_INIT_PASSWORD`）。

### 9. 检查容器健康状态

```bash
./scripts/healthcheck.sh
# 或
docker compose ps
docker inspect --format='{{.State.Health.Status}}' vp-backend
```

### 10. 检查前端页面和后端 API

```bash
curl -s http://127.0.0.1/api/health   # 应返回 {"status":"UP",...}
# 浏览器打开 http://服务器IP/ 访问登录页
```

### 11. 创建或初始化管理员账号

初始管理员由首次启动自动创建（见 B.8）。登录后可进入「用户与权限」创建更多账号、分配角色与授权网格。

### 12. 配置域名和 HTTPS

生产环境必须使用 HTTPS。推荐用 Nginx / Caddy 反向代理并申请证书：

- 将域名解析到服务器 IP；
- 用 `certbot`（配合 Nginx）或 Caddy 自动申请 Let's Encrypt 证书；
- 反向代理将 `443` 转发到本机的 `80` 端口（frontend 容器）。

示例（Caddy，自动 HTTPS）：

```caddyfile
your-domain.com {
    reverse_proxy 127.0.0.1:80
}
```

### 13. 配置防火墙

只开放必要端口：

```bash
sudo ufw allow 22    # SSH
sudo ufw allow 80    # HTTP（建议跳转到 443）
sudo ufw allow 443   # HTTPS
sudo ufw enable
```

> MySQL 容器**未对外暴露端口**，仅在后端内部网络可达，无需额外放行。

## C. 更新与回滚

### 1. 发布新版本

```bash
git tag v1.1.0
git push origin v1.1.0   # 触发工作流构建并发布 v1.1.0 镜像
```

### 2. 选择镜像版本

在服务器 `.env` 中确认目标版本，或直接传入脚本参数。

### 3. 执行镜像拉取

```bash
VERSION=v1.1.0 docker compose pull frontend backend
```

### 4. 执行备份（数据库 + 附件）

```bash
./scripts/backup.sh
```

脚本会同时产出两份：数据库 `backups/village_population_*.sql.gz`
与附件 `backups/uploads_*.tar.gz`。**两份必须成对保存**——附件的归属关系
（这张照片是谁的）在数据库里，缺任何一份都会导致照片找不到主人或彻底丢失。

### 5. 执行兼容的数据库迁移

后端启动时自动执行尚未应用的版本化迁移（`schema_migrations` 表记录已应用版本，幂等）。**升级前必须备份**（上一步已做）。

### 6. 重新启动应用

```bash
./scripts/update.sh v1.1.0   # 一键：备份 → 拉取 → 重启 → 健康检查
```

### 7. 检查健康状态和核心功能

```bash
./scripts/healthcheck.sh
```

浏览器验证：登录、人口列表、标签筛选、统计首页等核心功能。

### 8. 出现问题时回滚应用镜像

```bash
./scripts/rollback.sh v1.0.0   # 回滚到旧版本镜像
```

### 9. 数据库迁移后的回滚限制

- 应用镜像可随时回滚（镜像不可变，随时可用）。
- 数据库结构迁移**不可逆**（无法通过回滚镜像撤销）。若新版本的迁移改变了表结构且与旧应用不兼容，需从备份恢复数据库：
  ```bash
  ./scripts/restore.sh backups/village_population_<时间戳>.sql.gz
  ```

## D. 备份恢复

### 0. 附件（现场照片）存在哪里

附件**不在 docker 卷里**，而是绑载到宿主机的一个普通目录，默认 `deploy/data/uploads/`
（由 `.env` 的 `UPLOAD_DIR_HOST` 决定，容器内路径固定为 `/app/uploads`）。

这样选的原因：附件是唯一无法靠重新部署恢复的东西（数据库有迁移、代码有镜像、
照片丢了就是丢了）。绑宿主机目录后，备份就是复制一个文件夹，
也能在「某张照片在不在」这种问题上直接翻目录核对。

文件名本身就是「拍照时间-姓名-人员编号」（例 `20261016-193012-张三-P000123.jpg`），
所以不查数据库也能按时间找、按人对。

> 老部署是从命名卷 `village-population_uploads_data` 升上来的，
> 必须按 `deploy/README.md`「从 named volume 迁到宿主机目录」搬一次文件，
> 否则升级后照片会显示为「全部消失」（文件还在卷里，只是没人再看它）。

### 1. 定期备份（数据库 + 附件）

建议用 `cron` 每日备份：

```bash
crontab -e
# 每天凌晨 2 点备份（数据库 + 附件）
0 2 * * * /opt/village-population/scripts/backup.sh >> /var/log/vp-backup.log 2>&1
```

### 2. 备份文件保存在持久化存储或独立位置

备份输出到 `deploy/backups/`，请定期同步到独立存储（如对象存储、另一台机器），避免与数据同机丢失。

### 3. 备份文件不得公开

`backups/` 目录已在 `.gitignore`，请勿上传到公网，并限制文件访问权限。

### 4. 定期进行恢复演练

建议每月在测试环境演练一次恢复流程，确保备份可用。

### 5. 完整恢复命令

```bash
# 数据库（会覆盖现有数据，需输入 yes 确认）
./scripts/restore.sh backups/village_population_20260101_020000.sql.gz

# 附件：绑载目录是普通文件夹，解包即恢复（用同一时间戳的那一份）
tar -xzf backups/uploads_20260101_020000.tar.gz -C deploy
```

两份要一起恢复，且**时间戳要对得上**：只恢复数据库不恢复附件，
「现场照片」那一栏会是空的；只恢复附件不恢复数据库，
照片文件在磁盘上但没有归属记录，前台同样看不到。

### 6. 恢复前后检查步骤

- **恢复前**：确认目标备份文件完整（`ls -lh`）、确认当前数据已另做备份。
- **恢复后**：执行 `./scripts/healthcheck.sh`；登录系统核对总人口、家庭数、标签数据是否一致。

## E. 常见故障

**容器与卷速查**（Compose 项目名 `village-population`）：

| 用途 | 服务名 | 容器名 | 数据存放位置 |
|---|---|---|---|
| 数据库 | `mysql` | `vp-mysql`（仅 `internal` 网络，不对外开端口） | 卷 `village-population_mysql_data`（勿删） |
| 后端 | `backend` | `vp-backend` | 宿主机目录 `deploy/data/uploads/`（附件，`UPLOAD_DIR_HOST` 可改） |
| 前端 | `frontend` | `vp-frontend`（对外暴露 `${HTTP_PORT}`） | - |

### 镜像拉取失败

- 检查网络与 GHCR 认证（`docker login ghcr.io`）。
- 检查 `.env` 中镜像地址是否与真实仓库一致、`VERSION` 标签是否存在。

### GHCR 认证失败

- 私有镜像需先 `docker login ghcr.io -u 用户名` 并输入有 `read:packages` 权限的 token。
- 或到 Package 设置将镜像改为 Public。

### 数据库连接失败

```bash
docker compose logs backend   # 查看后端日志
```

#### 症状 A：`ER_ACCESS_DENIED_ERROR` / errno 1045

```
Error: Access denied for user 'village'@'172.19.0.3' (using password: YES)
code: 'ER_ACCESS_DENIED_ERROR', errno: 1045, sqlState: '28000'
```

**根因**：MySQL 只在数据目录为空（首次启动）时才根据 `MYSQL_USER` / `MYSQL_PASSWORD`  
创建应用账号。数据卷 `mysql_data` 一旦初始化完成，之后修改 `.env` 里的 `MYSQL_PASSWORD`  
**不会**同步到已存在的账号，后端用新密码连接即被拒绝。  
（网络与 `DB_HOST` 是通的——MySQL 能识别到来源 IP，说明是凭据问题而非连通性问题。）

**一键修复（推荐，不丢数据）**：

```bash
cd /opt/village-population
bash scripts/fix-mysql-auth.sh            # 默认读 deploy/.env
```

脚本会：核对后端实际环境变量 → 列出 MySQL 中的同名账号 → 按当前 `.env` 重建账号密码并授权 → 用应用账号自测连接 → 重启后端。

**手动修复**：

```bash
set -a; . ./.env; set +a
docker compose exec -T -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql mysql -uroot -e "
CREATE USER IF NOT EXISTS 'village'@'%' IDENTIFIED BY '$MYSQL_PASSWORD';
ALTER USER 'village'@'%' IDENTIFIED BY '$MYSQL_PASSWORD';
GRANT ALL PRIVILEGES ON village_population.* TO 'village'@'%';
FLUSH PRIVILEGES;"
docker compose restart backend
```

**彻底重建（会清空数据库，仅用于全新环境）**：

```bash
docker compose down -v        # 删除 mysql_data 卷
docker compose up -d
```

#### 症状 B：`.env` 写法导致密码被截断

- `.env` 中 `#` 及其后内容会被当作注释，密码含 `#` 会被截断；
- `$` 会被 Compose 当作变量引用展开，需写成 `$$`（最稳妥是干脆不用）；
- **不要加引号、前后不留空格**；建议密码只用字母数字（如 `openssl rand -hex 16` 生成）。

#### 症状 B2：`.env` 里仍是 `CHANGE_ME_*` 占位符

若数据卷早前已用其它密码初始化，而 `.env` 里是占位符（或相反），必然 1045。  
处理：把 `.env` 三个密码全部改为真实值，再执行 `bash scripts/fix-mysql-auth.sh` 同步账号；  
全新环境也可 `docker compose down -v && docker compose up -d` 直接按当前 `.env` 重建。

#### 症状 C：MySQL 尚未就绪

后端已配置 `depends_on: mysql (condition: service_healthy)`，会等待健康检查通过后再启动；  
若仍出现在 MySQL 初始化期间连上，执行 `docker compose restart backend` 即可。

### 端口冲突

- `HTTP_PORT` 被占用：修改 `.env` 中 `HTTP_PORT` 为其它端口。

### 容器反复重启

```bash
docker compose logs backend --tail 100
```

常见原因：环境变量缺失、数据库连接失败、JWT_SECRET 未配置。

### 前端无法访问后端

- 确认 `frontend` 容器 Nginx 反向代理指向服务名 `backend`（已在镜像内固定配置）。
- 浏览器打开 F12 查看 `/api` 请求是否 502，检查 `docker compose logs frontend`。

### 数据库迁移失败

- 迁移脚本按版本号执行，失败会回滚整个事务并中止启动。
- 查看后端日志定位失败版本，修复前请勿删除 `schema_migrations` 表数据。

#### 症状：`Table 'village_population.sys_user' doesn't exist`（errno 1146）

**根因**：2026-10-10 之前的镜像使用了有缺陷的 SQL 解析器（按 `;` 拆分后丢弃以 `--` 开头的块），
迁移 SQL 中「注释 + 建表语句」的组合被整体静默丢弃——V001 的 25 条语句只执行了 2 条，
但版本号仍被记入 `schema_migrations`，后续启动都会跳过迁移，表现为表不存在。

**修复**：已修复解析器（正确处理字符串内分号/行注释/块注释）并新增两道防护
（迁移目录为空、单文件解析出 0 条语句时直接报错拒绝启动）。

**处理**：拉取新镜像后，由于库内 `schema_migrations` 已记录错误版本、表结构残缺，
必须重置数据库（全新部署无数据，直接重建即可）：

```bash
docker compose pull
docker compose down -v        # 清掉被污染的半套 schema（会清空数据库）
docker compose up -d
docker compose logs -f backend # 应看到：[migrate] 已应用 V001__init_schema.sql（25 条语句）
```

### 磁盘空间不足

```bash
df -h
docker system df          # 查看镜像/卷占用
docker system prune -a    # 清理无用镜像（谨慎）
```

- 检查 `backups/` 是否长期未清理（备份脚本默认保留 30 份）。
- 日志已通过 `json-file` + `max-size` 限制轮转。

### 备份恢复失败

- 确认备份文件完整（非空、可 `gunzip -t` 校验）。
- 确认恢复前 MySQL 容器运行中，且 `.env` 中 root 密码正确。

## F. NAS 部署（从 GHCR 拉取镜像）

适用场景：GitHub Actions 自动构建镜像发布到 GHCR → 在 NAS（x86_64 机型）上拉取并部署。  
整个流程 NAS 上**只需要 `deploy/` 目录**，不需要 Node.js、不需要在 NAS 上构建。

### 前置条件

- NAS 为 **x86_64（Intel/AMD）** 架构（终端执行 `uname -m` 确认；若为 aarch64 需联系仓库维护者恢复 arm64 构建）
- NAS 已安装 Docker Engine 与 **Docker Compose v2**（`docker compose version` 应为 v2.x；老的 `docker-compose` v1 不支持本配置）

### 1. 将 GHCR 镜像设为 Public（一次性，必做）

CI 使用 `GITHUB_TOKEN` 推送镜像，包默认是**私有**的，NAS 匿名拉取会报 `unauthorized: authentication required`。  
该设置没有对应 API，需在网页操作（两个包各一次）：

1. 打开仓库主页 → 右侧 **Packages** → 点进 `village-population-system-backend`
2. 右侧 **Package settings** → 底部 **Danger Zone** → **Change visibility** → 选 **Public** → 输入包名确认
3. 对 `village-population-system-frontend` 重复同样操作

验证（无需登录即返回 JSON 即为成功）：

```bash
curl -s https://ghcr.io/token?scope=repository:0uzu0/village-population-system-backend:pull | head -c 100
```

> 若坚持私有：NAS 上执行 `docker login ghcr.io`（用户名 + `read:packages` 权限的 classic PAT）即可，其余步骤相同。

### 2. 上传部署文件到 NAS

只需要 `deploy/` 目录（compose 文件、.env.example、scripts/）：

```bash
scp -r deploy/ user@nas:/volume1/docker/village-population/
ssh user@nas
cd /volume1/docker/village-population
```

### 3. 配置 .env

```bash
cp .env.example .env
vi .env    # 或用任何编辑器
```

需要修改的项（`.env.example` 中镜像地址已预填真实仓库）：

| 变量                                       | 说明                                                                    |
| ---------------------------------------- | --------------------------------------------------------------------- |
| `VERSION`                                | `latest`（每次先 `docker compose pull`）或 `sha-xxxxxxx` / `v1.0.0`（见文件内注释） |
| `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` | 数据库密码，**只用字母数字与 `-_`**，单引号包裹                                          |
| `JWT_SECRET`                             | `openssl rand -hex 32` 生成                                             |
| `ADMIN_INIT_PASSWORD`                    | 首次启动自动创建的管理员密码                                                        |
| `HTTP_PORT`                              | NAS 上 80 常被系统占用，建议改如 `8088`                                           |

### 4. 启动

```bash
docker compose up -d        # 首次会拉取镜像、建库、跑迁移、创建管理员
docker compose ps
bash scripts/healthcheck.sh
```

浏览器访问 `http://NAS_IP:HTTP_PORT` 登录（管理员账号见 `.env` 的 `ADMIN_INIT_*`）。

### 5. 日常更新与回滚

```bash
bash scripts/update.sh v1.1.0      # 更新到指定版本（先在 GitHub 打 git tag v1.1.0 触发构建）
bash scripts/update.sh latest      # 或：直接追最新（脚本内会先 docker compose pull）
bash scripts/rollback.sh v1.0.0    # 回滚（数据库结构迁移不可回滚，见 C 节）
```

建议：日常备份交给 `scripts/backup.sh` + crontab（见 D 节），NAS 上至少保证 `backups/` 有近期备份。

### 常见坑（NAS 场景）

- **拉取 `ghcr.io` 超时**：部分网络环境访问 ghcr.io 不稳定。可选方案：  
  在能访问的机器上 `docker pull` + `docker save -o img.tar` + 传到 NAS 后 `docker load`；  
  或给 NAS 的 Docker daemon 配置 HTTP 代理（群晖：`/etc/systemd/system/docker.service.d/http-proxy.conf`）。
- **80 端口冲突**：群晖等 NAS 自带 Web 服务占用 80，务必改 `HTTP_PORT`。


- **`no matching manifest for linux/arm64`**：说明 NAS 是 ARM 机型，当前镜像仅含 amd64。
- **MySQL 1045 鉴权失败**：见 E 节「数据库连接失败 / 症状 A」，用 `scripts/fix-mysql-auth.sh` 一键修复。
- 生产环境必须启用 HTTPS。
- 所有密码、`JWT_SECRET` 通过 `.env` 注入，不写入镜像或代码。
- 密码使用 bcrypt 哈希存储，生产环境必须启用 HTTPS。
- 导出、批量修改、权限调整均有审计日志。
- 备份文件受访问控制，不进入版本库。
