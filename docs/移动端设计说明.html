01为什么做移动端

现有系统是「坐在村委电脑前，对着大表格录入和核对」的形态，这件事它做得很好。 但村级工作里有一大块时间是在**外面**的：入户走访、上门登记、现场核查、拍照留痕。 这部分工作目前只能先记在纸上或手机备忘录里，回来再补录——于是要么漏，要么错， 要么补录时已经想不起当时的情况。

问题一：信息在现场，录入在办公室

走访时对方报的身份证号、电话号码、家庭情况，当时的准确率最高。 等到回办公室再录，靠的是记忆和潦草的手写笔记。

问题二：照片拍在手机里，没进系统

现场照片留在个人手机相册里，既不是系统的证据链，也不受权限管控， 人员调动后这些材料就散了。

问题三：台账是事后补的

水利、民政、卫健这些条口的日常工作量，往往是月底集中回忆着填报， 数据质量和可信度都不高。

设计目标不是「把电脑端的页面塞进手机」。 手机屏幕小、输入慢、还经常没信号，硬搬只会得到一个谁都不用的 App。 目标是：把「必须在外勤现场完成」的动作做顺，其余一律留在电脑端。

02职责边界：做什么，不做什么

这条线是本次设计里最重要的一个决定。功能范围靠「这件事能不能站着、用一只手、 在可能没网的院子里做完」来划，而不是靠「技术上能不能实现」。

✓ 移动端承担

  • 查人：按姓名 / 身份证号 / 手机号搜，按村庄、人群筛
  • 看人：基本信息、重点人群标签、残疾档案、联系方式、变更历史
  • 登记：新增人员（身份证号自动带出出生日期与性别）
  • 改状态：迁入 / 迁出 / 死亡（只改状态，不删人）
  • 打标签：重点人群标签的加与减
  • 拍照留痕：现场照片直接进系统文件库，关联到人
  • 台账速记：条口工作量的现场即时录入 + 附件
  • 待核查处理：逐条补齐或忽略导入时身份证号有问题的记录
  • 看板：在册人口、各重点人群数量（含缓存兜底）

✗ 刻意不做（留在电脑端）

  • Excel 导入导出——要在大屏幕上核对表头、看失败行明细
  • 用户 / 角色 / 权限管理——这是管理员的事，且有误操作风险
  • 标签字典维护——低频、影响面大，手机上改容易出事
  • 审计日志——只适合查询和翻页浏览
  • 家庭批量按门牌号归户——需要横向比对整张表
  • 统计报表——图表在 5 吋屏上读不出信息量

这些不做，不是没时间，是做不好。留一个功能不完整但好用的手机端， 比做一个什么都有但处处别扭的要强。

权限零新增。App 只调用后端已有的 /api 接口，走同一个鉴权中间件、 同一套权限码（person:view / person:manage / ledger:manage …）。 服务端没有为移动端开任何后门或旁路——所以不可能出现「手机能绕过权限」的问题， 权限调整也只需在一处改。

03信息架构与导航

四个底部 Tab，顺序按「实际使用频次」排：查人最多，其次是看板， 再次是待核查，最后才是「我的」。刻意压到 4 个，不用汉堡菜单—— 目标用户里不少人不熟悉侧滑抽屉这类交互。

工作台· 人口· 待核查 角标· 我的

页面流转

启动→ 读服务器地址 + Token→ 登录→ 工作台
工作台→ 重点人群卡（带筛选条件）→ 人口列表→ 人员详情→ 编辑 / 拍照
工作台→ 台账速记→ （附现场照片）→ 保存

两个非功能性约定

字号整体比 Material 默认大一号

标题 22sp、正文 17sp。使用者是村干部和网格员，相当一部分人戴老花镜。 在「看起来精致」和「看得清」之间，这个应用的排版只守一条硬规则：选看得清。

登录失效不做静默跳转

Token 过期时弹一个确认框，写明原因，并明确告知「未上传的走访记录仍保存在本机， 重新登录后可继续同步」。最糟的处理是用户正在填表单时被无声弹回登录页—— 他会以为数据丢了，然后放弃使用。

05接口映射

全部为后端已有接口，未新增任何端点。列出的第二个用途是「这一行最容易踩的坑」， 这些坑都是从现有实现里读出来并逐一处理的。

页面 / 动作接口关键约定与坑
登录POST /api/auth/login返回 token 与权限码数组；后端对登录有频率限制，失败文案要原样展示
身份校验 / 角色GET /api/auth/me冷启动用它确认 token 是否还有效
修改密码PUT /api/auth/password无返回体
人口列表GET /api/personsactiveOnly 是字符串 "true"（后端为 z.enum），传布尔会 400
人员详情GET /api/persons/{id}详情才带残疾档案与变更历史；列表行不含这些
新增 / 编辑POST / PUT /api/persons编辑时出生日期由身份证号派生并覆盖表单旧值；null 字段不参与序列化
加 / 减标签POST /api/persons/{id}/tags
DELETE /api/persons/{id}/tags/{linkId}		加标签一次只收一个 tagId（不是数组）
村庄下拉GET /api/grids/villages返回 {list,total}，没有 page/pageSize；村庄负责人/电话由该接口一并带出
重点人群卡片GET /api/key-groups/quick返回 byAge/minAge/maxAge；年龄类按区间筛、身份类按标签筛，两者不能混
首页看板GET /api/statistics/dashboard只统计在册人口（正常 / 迁入）
待核查列表 / 汇总GET /api/pending
GET /api/pending/summary		角标数字取自 summary
确认 / 忽略POST /api/pending/{id}/confirm
POST /api/pending/{id}/ignore
POST /api/pending/batch-ignore		确认入库要求身份证号合法；不做离线排队（见 06 节）
台账表单配置GET /api/ledgers/meta条口与工作类型由后端配置下发，客户端不写死编码
台账列表 / 新建GET / POST /api/ledgers/records宽表：类别 / 类型 / 日期 / 劳务费 / 发票金额 / 发票号 / 责任人 / 地点 / 标题 / 备注
上传附件POST /api/files/upload返回单个对象（不是数组）；类型白名单 .pdf/.jpg/.jpeg/.png/.webp，不限大小
预览 / 下载附件GET /api/files/{id}需要 Bearer 头，不能把 URL 直接丢给图片控件——必须取字节流再由客户端渲染
统一响应信封。所有接口返回 { code, message, data, errorCode }， code == 0 才是成功；失败时后端把 HTTP 状态码写进 code。 客户端把「HTTP 200 但 code≠0」和「真 HTTP 4xx/5xx」两种情况收敛成同一个异常类型， 避免出现「业务错误被当成功、页面莫名其妙是空的」。

06离线设计

这是整个移动端最核心的部分。村里的网络不是「快和慢」的区别，而是 「有和没有」的区别——院墙厚一点、走到村东头，信号就没了。 所以这里做的不是「加载失败给个重试按钮」，而是分级降级 + 写操作排队。

读：三级降级

第 1 级
直接请求服务端 网络正常时总是走这一条，数据最新。
第 2 级
落到本地缓存，并在页面顶部显示醒目横幅 缓存按查询条件分别落盘（一个查询一个文件），命中率高。 横幅写明「这是本地缓存数据（2 小时前），只可作为参考，上报口径请以联网结果为准」—— 绝不让缓存数据看起来像实时数据，这是最容易造成「数据不准」投诉的坑。
第 3 级
无缓存可用时，明确报错并提供重试 不显示空白页、不复用别的查询条件的数据。
只有「网络类异常」才降级。业务错误（权限不足、参数非法、登录失效）必须原样抛出来， 不能被缓存兜住——否则用户会看着一份旧数据、以为操作成功了， 这是比「打不开」严重得多的问题。

写：离线队列

写操作失败（且失败原因是网络）时，这次操作不会丢，而是序列化成一条记录落到本地队列， 同时给用户明确反馈「已暂存，联网后自动上传」。

设计点做法为什么
存储形式一个操作一个 JSON 文件损坏只影响一条；不需要引入数据库与注解处理器
执行顺序严格先进先出同一条走访路线上先采的人先入库，避免「家庭成员引用了还没建的人」
重试上限5 次到顶后保留在列表里并写明原因，由人工处理，不再自动重试
网络不通立刻中止整轮不逐条重试到底——村里信号时有时无，连续重试只耗电。剩余重试次数留给下一次系统调度
业务性失败一次到位标记「重试到底」身份证重复、校验位错误这类错误重试一万次结果一样，只会让队列看起来永远同步不完
登录失效停止并通知界面继续重试只会反复 401
触发时机冷启动、进入前台、手动下拉，以及 6 小时定期兜底系统级后台调度不保证准时，定期任务只是保底
退出登录保留未上传队列退出登录或 token 过期不该让现场采集的数据消失
本地缓存与离线队列是两个目录，互不干扰。 清理缓存绝不能碰到未上传的数据——这个约束靠目录分离来保证，而不是靠代码里的调用顺序。
「待核查确认入库」不做离线排队，必须联网。 因为它的前置条件是身份证号要合法，而合法性校验依赖服务端对唯一性的判断； 在本地排队等于放一个可能永远失败的操作用户却看不到。这一条是刻意的例外。

07技术选型与理由

选择理由放弃了什么
Kotlin + Jetpack Compose 声明式 UI 写表单和列表更快；与现有技术栈一样可以只用一套语言；Compose 的表单状态管理比 XML + ViewBinding 少一半样板代码 放弃 XML 布局的成熟插件生态
手写依赖装配
不用 Hilt / Koin		 全应用只有一个单例容器。手写装配比引入注解处理器更省编译时间，也少一层「看不懂的魔法」，出问题能直接读代码定位 依赖多了以后要手工维护构造函数
文件式 JSON 缓存
不用 Room		 缓存的数据形态就是「查询条件 → 一坨 JSON」，不需要关联查询和事务。更关键的是：不用 Room 就不用 KSP，CI 少一个易出错环节、注解处理时间归零 失去类型安全的查询和自动迁移
kotlinx.serialization 与 Kotlin 同为 JetBrains 出品，编译期生成序列化器，无需反射；对 null 的处理可以精确控制 相比 Gson 需显式标注
Retrofit + OkHttp 拦截器机制正好用来解决「服务器地址运行时可改」这个刚需；连接/读写超时可分别放宽（上传大图需要 120s 写超时） 无
WorkManager 系统级后台调度，带网络约束与指数退避，被杀后系统会重新拉起；比自己写 Service 可靠 精确执行时间不可控（因此另有 6 小时定期兜底）
DataStore 存 token 与服务器地址，替代已废弃的 SharedPreferences 异步读取不适合拦截器，故另有内存镜像（见下）

一个必须解释的设计：服务器地址为什么放在拦截器里

本项目有一个别处不常见的约束：同一个 APK 要分发给几十个村，各村的 NAS 地址不一样。 如果服务器地址在编译期写死，就得给每个村单独打一个包。

所以 Base URL 只在打包时作为默认值注入，真值存在本地、可在 App 内随时修改。 但这里遇到一个技术冲突：

OkHttp 的拦截器是同步的，而 DataStore 只能异步读取——在拦截器里 runBlocking 读 DataStore 会卡住网络线程并可能死锁。

解法：token 与服务器地址在启动时读一次进内存，拦截器只读这个内存镜像； 修改地址时同步更新镜像。代价是冷启动必须先完成这一步然后才能发请求， 所以启动时会显示「正在启动…」，而不是先发一个注定打到占位地址的请求。

UI 层的两个对应处理

  • 「HTTP 200 + code≠0」当失败抛异常——后端大量业务错误是这个形态 （比如「账号或密码错误」）。只 catch HTTP 异常的话，这类错误会被当成功， 页面莫名其妙是空的，而且没人知道为什么。
  • 异常信息要翻译成人话。宁可说「网络不可用，请检查网络或服务器地址」， 也不要把 Expected URL scheme 'http' or 'https' 这种英文栈信息甩给网格员。

08安全设计

权限：零新增、零旁路

App 调用的全部是后端已有接口，走同一套鉴权中间件与权限码。 客户端还按登录返回的权限码决定菜单与按钮是否可见—— 但这只是体验优化，真正的拦截始终在服务端。

Token 不入日志

debug 构建会打网络日志，但 Authorization 头被显式脱敏。 原因很实际：logcat 在真机上别的应用也能读。

权限只要该要的

清单里没有 CAMERA、没有存储权限、没有定位权限，只有 INTERNET 与 ACCESS_NETWORK_STATE。做法是：

  • 拍照走系统相机的 ACTION_IMAGE_CAPTURE，把应用私有目录里的临时文件通过 FileProvider 授权给它
  • 选图走系统文件选择器（SAF），由系统把 URI 授权给本应用
  • 打电话用 ACTION_DIAL（只是跳到拨号盘）而不是 ACTION_CALL（直接拨出）

明文 HTTP：为什么允许，边界在哪

后端部署在村委内网 NAS 上，没有可用的 HTTPS 证书， 强行要求 HTTPS 等于这个 App 根本连不上。

做法是在网络安全配置里放行明文，并把这条理由写在配置文件里， 而不是简单地在清单上开 usesCleartextTraffic 一了百了。 同时明确：这不是给公网部署用的方案——若要上公网，后端必须先上 HTTPS。

不在客户端做数据裁剪

「这个人该不该被当前用户看到」由服务端按数据范围决定。 客户端不做「拉全量再过滤」——那等于把不该看的数据下载到了手机上。

身份证号的显示

列表与详情按脱敏形式显示（保留前 6 后 4）； 但校验逻辑用完整值——客户端实现的是与后端 backend/src/utils/idcard.ts 同口径的校验算法 （15 位升 18 位、校验位、不存在的月日如 02-30 判为非法）。

年龄口径在两端必须一致。客户端实现了一份服务端口径的镜像：出生日期以身份证号为权威来源， 年龄用「年月日三元组比较」而不是「毫秒差除以 365」——后者在闰年和生日当天都会差一岁。 「60 岁及以上」与「18 岁以下」是重点人群的判定线，差一岁就是名单里多一个人或少一个人。

09打包与发布

用 GitHub Actions 自动打包，不再依赖任何一台开发机。三条触发路径覆盖全部场景。

触发产出用途
push 到 main（且改动涉及 android/**） village-app-debug-<sha7>.apk + village-app-0.0.<run>.apk（release） 每次提交都出两个包：debug 供测试机安装，release 供实际分发
Pull Request 到 main 单元测试报告 + debug APK 合并前拦住回归；测试报告失败时也上传，便于定位。不出 release，省 CI
打 v* 标签 village-app-<版本>.apk（release） 作为正式版本发布到 GitHub Release 页面
手动触发（workflow_dispatch） release APK（可用 build_release 关掉），可指定服务器地址 需要临时给某个村出一个指向特定地址的包时用

几个关键决定

路径过滤 + 标签推送

只有动了 android/** 才跑，避免改前端、后端也白烧几分钟 CI。 但 GitHub 官方明确路径过滤器不对标签推送生效， 所以打 v* 标签时一定会出包——这正好是我们想要的行为。

签名缺失时回退 debug 签名

仓库里不放签名文件。4 个签名密钥全部配齐时 release 包用正式签名； 缺任意一项就回退到 debug 签名，并在日志与 Job Summary 里明确提示。 目的是保证流水线永远给出一个「能装上、能跑」的 APK， 而不是一个谁也装不了的 unsigned 包。

⚠️ 只配了 ANDROID_KEYSTORE_BASE64 是最常见的坑：那时 Gradle 会 因为口令为空直接报错，结果是一个 release 包都出不来。所以密钥按「全配或全不配」处理。

⚠️ debug 签名的 release 包与正式签名包签名不同，同名应用覆盖安装会失败， 换正式包前需要先卸载。

R8 暂不开启

kotlinx.serialization 靠「编译期生成的序列化器 + 反射查找 Companion」工作， 混淆规则写不对的典型症状是「能装上、一进页面就崩」—— 而这类问题只有真机冒烟才能发现，CI 编译通过不代表没问题。 所以先用不混淆的 release 包把链路跑通，规则已提前写好，真机验证后再打开。

debug / release 可共存

debug 包的应用 id 带 .debug 后缀、版本名带 -debug， 两个包能同时装在一台手机上——现场排查问题时这一点很有用。

产物文件名必须 ASCII

GitHub 会把 Release 附件名里的非 ASCII 字符直接删掉（官方 API 文档： GitHub renames asset filenames that have special characters, non-alphanumeric characters, and leading or trailing periods）。 实测「掌上村务-1.0.0.apk」上传后变成「-1.0.0.apk」——包是好的，名字像坏的。 所以产物统一叫 village-app-*.apk，中文只出现在 Release 说明文字里。

需要的仓库密钥（四个必须齐全，否则回退 debug 签名）

ANDROID_KEYSTORE_BASE64     keystore 文件的 base64（base64 -w0 release.jks > keystore.txt）
ANDROID_KEYSTORE_PASSWORD   keystore 口令
ANDROID_KEY_ALIAS           密钥别名
ANDROID_KEY_PASSWORD        密钥口令

注入打包参数

./gradlew assembleRelease \
  -PversionCode=<CI run number> \
  -PversionName=<标签去掉 v，如 1.2.3> \
  -PapiBaseUrl=http://192.168.1.100:8080/

服务器地址只是默认值，装到手机上还能在「我的 → 服务器地址」里改， 所以同一个包可以发给多个村。

还没有做的事：真机冒烟测试。 单元测试只能证明「逻辑对、能装上」，证明不了「在村里的手机上跑得顺」。 上线前至少要在一台真实设备上走完整流程：登录 → 查人 → 新增 → 拍照 → 断网 → 恢复网络 → 确认队列自动上传成功。 这一步不做，不建议把这个包发给村里用。

11已知取舍与后续

取舍 / 缺口现状后续怎么做
R8 未开启 release 包未混淆，体积 12.3 MB 真机验证后打开 isMinifyEnabled；规则已备好，预计可再瘦 2–3 MB
无真机测试 只做了编译 + 单元测试 补一台真机的冒烟流程（见 10 节）；之后考虑加 Compose UI 测试
离线冲突未处理 队列只按时间顺序重放，不检测「服务端已被别人改过」 可加乐观锁（updated_at 比对），冲突时提示用户保留哪一份
缓存不过期 有缓存就直接用，只显示「多久之前」 可加「超过 N 天的缓存不参与降级」，避免长期离线看到过时数据
家庭管理未接入 手机上只看家庭户数，不做按门牌号归户 刻意不做。若将来需要，应做「查看家庭成员」而非「归户操作」
无崩溃上报 崩溃只能靠用户口述 村级内网环境不适合接第三方服务；可在本机落崩溃日志，由用户手动导出
定位能力未用 没有申请定位权限 这是刻意的：走访留痕靠照片和时间，采集定位会显著增加权限阻力与合规成本
一句话总结这次设计的取舍原则： 凡是「在手机上做会比在电脑上做更差」的功能，一律不做； 凡是「只能在外勤现场做」的功能，哪怕技术上有难度（离线队列、运行时服务器地址、 不申请权限的拍照）也要做扎实。
