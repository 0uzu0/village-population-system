# 更新与回滚说明

## 一、镜像版本管理策略

> **v 前缀（重要）**：git 标签是 `v2.2.3`，镜像标签是 `2.2.3`——`docker/metadata-action`
> 的 `pattern={{version}}` 会去掉 `v`。`.env` 里的 `VERSION` 填的是**镜像标签**，所以
> 应写 `VERSION=2.2.3`。`scripts/update.sh` / `rollback.sh` 两种写法都接受（会自动去掉 `v`）；
> 手动执行 `docker compose pull` 时不要带 `v`。
> （2026-10-18 起工作流额外推送 `v{{version}}` 别名，下一个标签之后两种写法都能拉到。）

| 镜像标签 | 对应 git 标签 | 含义 | 是否可覆盖 |
|------|------|------|-----------|
| `latest` | — | main 分支最新稳定构建（开发预览用） | 是 |
| `sha-<短哈希>` | — | 每次提交对应的唯一镜像 | 否（随提交不可变） |
| `2.2.3` | `v2.2.3` | **当前正式版本**（2026-10-18 安卓端现场照片加载修复） | 否 |
| `2.2.2` | `v2.2.2` | 历史正式版本（标签编码归一） | 否 |
| `2.2.1` | `v2.2.1` | 历史正式版本（V021 启动崩溃热修） | 否 |
| `2.2.0` | `v2.2.0` | ⚠️ **有缺陷，勿用于新部署**（启动即崩，见「四」的说明） | 否 |
| `2.1.1` | `v2.1.1` | 历史正式版本 | 否 |
| `2.1.0` | `v2.1.0` | 历史正式版本 | 否 |
| `2.0.2` | `v2.0.2` | 历史正式版本 | 否 |
| `2.0.1` | `v2.0.1` | 历史正式版本 | 否 |
| `2.0.0` | `v2.0.0` | 历史正式版本 | 否 |
| `1.0.8` | `v1.0.8` | 历史正式版本 | 否 |
| `1.0.7` | `v1.0.7` | 历史正式版本 | 否 |
| `1.0.6` | `v1.0.6` | 历史正式版本 | 否 |
| `1.0.5` | `v1.0.5` | 历史正式版本 | 否 |
| `1.0.4` | `v1.0.4` | 历史正式版本 | 否 |
| `1.0.3` | `v1.0.3` | 历史正式版本 | 否 |
| `1.0.2` | `v1.0.2` | 历史正式版本 | 否 |
| `1.0.1` | `v1.0.1` | 历史正式版本 | 否 |
| `1.0.0` | `v1.0.0` | 历史正式版本 | 否 |

- **开发镜像**：`latest`、`sha-<哈希>`，用于联调与预览。
- **正式发布镜像**：`X.Y.Z`（由 git 标签 `vX.Y.Z` 触发构建），不可变，用于生产。
- 生产环境 `.env` 中的 `VERSION` 应固定为 `X.Y.Z`，禁止长期使用 `latest`。
- **没有** `2.2` / `2` 这类次版本、主版本浮动指针，也没有 `2.1.2` 镜像：
  v2.1.2 只改过 `package.json` 的版本号，没有打标签，因此既没有 Release 也没有镜像，
  不能作为回滚目标（回滚请用 `2.1.1`）。

## 二、升级流程

```bash
cd deploy
./scripts/backup.sh              # 1. 备份数据库与附件（必须，两份成对）
VERSION=2.2.3 docker compose pull frontend backend   # 2. 拉取新镜像（注意不带 v）
./scripts/update.sh v2.2.3       # 3. 一键：备份→拉取→重启→健康检查
```

或手动：

```bash
./scripts/backup.sh
VERSION=2.2.3 docker compose pull frontend backend
sed -i 's/^VERSION=.*/VERSION=2.2.3/' .env
VERSION=2.2.3 docker compose up -d frontend backend
./scripts/healthcheck.sh
```

数据库结构迁移在后端启动时自动执行（幂等，通过 `schema_migrations` 表记录已应用版本）。

## 三、回滚流程

```bash
./scripts/rollback.sh v2.1.1     # 回滚应用镜像（写 2.1.1 也可以）
./scripts/healthcheck.sh
```

脚本只做 `docker compose up -d`，不回退数据库。若目标镜像在本机已被清理（`docker image prune`），
需要先手动 `VERSION=2.1.1 docker compose pull frontend backend` 再执行回滚。

## 四、数据库迁移后的回滚限制（重要）

### ⚠️ v2.2.0 的启动崩溃与 v2.2.1 的自愈（2026-10-18 事故）

**现象**：v2.2.0 在有数据的老库上后端起不来，容器反复重启，日志里循环刷
`migration-failed: V021__tag_exclusive_group.sql / Duplicate column name 'exclusive_group'`。

**原因**：迁移执行器把整个 SQL 文件包在一个事务里，但 **MySQL 的 DDL 会隐式提交**——
`ALTER TABLE` 一旦执行成功就收不回来了。v2.2.0 的 V021 是「ALTER 加列 + 若干 DML」的多语句
文件，ALTER 成功、后面的语句失败（同表相关子查询触发了 MySQL 的
`ER_UPDATE_TABLE_USED(1093)`）→ `rollback` 无效、版本号没写进 `schema_migrations` →
下次启动再从第一条 ALTER 开始，直接撞「列已存在」。

**v2.2.1 怎么修**：
1. V021 改成**可重跑**：加列前先查 `information_schema`，列已存在就跳过（MySQL 8.0 不支持
   `ADD COLUMN IF NOT EXISTS`，所以用动态 SQL）；列注释用幂等的 `MODIFY COLUMN` 补，
   让「新库」和「事故后重跑」两条路径最终表结构完全一致。
2. 存量收口改用 V017/V019 已经验证过的**自连接**写法，不再用同表相关子查询。
3. 迁移执行器失败时打印**第几条语句**、语句前 160 字和 errno，下次不用再靠猜。

**升级到 v2.2.1 时不需要手工动数据库**：旧的半应用状态会被自动识别并跳过已加的列，
后续 DML 正常执行，然后写入版本号。如果当初 V021 已经跑完、只是版本号没记上，重跑同样安全
（所有语句都是幂等的，干净数据影响 0 行）。

### v2.2.2：标签编码归一（2026-10-18）

**背景**：标签管理页允许手填编码，且不校验重名。有人建了一枚「流动人口」但编码填成
`FLOATING_PERSON`（系统规范编码是 `FLOATING_POP`）并给人员打上，于是出现：
标签页显示 N 人、工作台流动人口恒为 0——工作台是按 `td.code` 取数的，认不出这个编码，
而且全程不报错。

**v2.2.2 做了三件事**：
1. **V023 迁移**把「与系统标签同名（或编码是已知别名）的自定义标签」合并到系统标签：
   人员关联改指向系统标签、重复关联停用（防止同一人被数两次）、自定义标签停用并保留在原处
   （历史流水仍能看出它原名）。**升级后工作台的户籍/流动数字会自动恢复**，不需要手工改数据。
2. 写入侧防呆：新建标签时拦「同名标签」与「别名编码」，并提示应使用的规范编码；
   系统内建标签的**编码不可修改**（名称/颜色/说明照常可改）。
3. 启动自检：系统标签缺失或被停用时，容器日志打 `system-tag-missing` / `system-tag-disabled`
   告警——这类问题以前是完全静默的。

**排查工具**：`deploy/scripts/diag-system-tags.sql`（只读），一次输出系统标签台账、
重名标签、各标签的生效/停用关联数、被「户籍优先」压制的人数，以及与后端代码逐字一致的
工作台实际计数。

### v2.2.3：安卓端现场照片加载修复（2026-10-18）

**背景**：人员详情页在照片慢加载或加载失败时会卡住，甚至闪退。根因有两条，都在客户端：

1. **下载跑在主线程**。取图函数的调用方是 Compose 的 `produceState`，它运行在组合的
   协程上下文里（= 主线程），而 `/files/:id` 接口是 `@Streaming` 的——读响应体是同步阻塞的。
   于是每张照片都要主线程原地等它下完，弱网下一张就能堵十几秒。
2. **整张原图读进内存**。原来是先 `bytes()` 读成 `ByteArray` 再写盘，等于一份常驻堆、
   一份写入缓冲。照片区是 FlowRow（不是懒加载），进详情页会同时开始下载该人的全部照片，
   二十张原图轻松上百 MB，低端机直接 OOM。

**v2.2.3 做了三件事**（只改 `android/`，后端与 Web 端代码未变）：
1. 取图全程切到 IO 线程，并改成**边下边写**，不再经过内存中的整个字节数组。
2. 落盘前后校验：先写 `.part`、确认是 JPEG/PNG/WebP 才改名；缓存命中时也验一次文件头，
   遇到旧版本留下的坏文件自动删掉重下（这类文件以前会「永远打不开」，因为命中缓存就不再下载）。
3. 缩略图区分「加载中 / 失败 / 成功」三态：失败显示「点按重试」而不是一直转圈；
   放大查看同样带重试，并把解码尺寸限在 1440px 以内，避免超大原图把内存顶穿。

**镜像内容与 2.2.2 一致**：这次只动了安卓端，镜像是同源码重建的，升级镜像本身没有行为变化；
真正要换的是 App。装 `village-app-2.2.3.apk` 覆盖安装即可（versionCode 递增，可直接升级）。

### 2.2.x 的回滚兼容性（可用镜像回滚，无需恢复数据库）

v2.2.0 / v2.2.1 / v2.2.2 新增的四个迁移**均为加列 + 存量收口**，不改动、不删除任何既有列：

| 迁移 | 内容 | 旧版本（≤2.1.1）是否受影响 |
|------|------|--------------------------|
| `V020__user_token_version.sql` | `sys_user` 加 `token_version` | 否，旧代码不读该列 |
| `V021__tag_exclusive_group.sql` | `tag_definition` 加 `exclusive_group` / `exclusive_priority` | 否，旧代码不读这两列 |
| `V022__person_row_version.sql` | `person` 加 `row_version` | 否，旧代码不读该列 |
| `V023__merge_duplicate_system_tags.sql` | 把同名自定义标签的人员关联并入系统标签，停用自定义标签 | 否，只是标签定义与关联变了，旧代码按编码查反而**恢复正常** |

所以 v2.2.x 出问题时**可以直接把镜像回滚到 2.1.1，不需要恢复数据库**。唯一的副作用是：V021 会把同组内优先级更低的生效标签置为停用（例如已有「户籍人口」时停用「流动人口」）。回滚到旧版本后这些标签仍是停用状态，旧版本的户籍/流动互斥逻辑不会自动把它们恢复——如需完全复原，把停用的标签手动改回生效即可（或在旧版本里重新打一次该标签）。

其它版本（迁移修改既有表结构时）仍按下述流程处理。

- **应用镜像**：可随时回滚到任意旧版本，镜像不可变，随时可用。
- **数据库结构**：迁移不可逆。若新版本迁移修改了表结构且旧应用不兼容，回滚镜像无法解决，必须**从备份恢复数据库**：

```bash
# 先停掉后端，避免回滚期间写入
docker compose stop backend
# 从升级前的备份恢复
./scripts/restore.sh backups/village_population_<升级前时间戳>.sql.gz
# 重启后端
docker compose up -d backend
```

## 五、升级前检查清单

1. 已备份数据库并确认备份文件非空。
2. 已阅读新版本的数据库迁移脚本（`backend/src/db/migrations/`）。
3. 已准备旧版本镜像标签，便于回滚。
4. 业务低峰期执行，并在升级后验证核心功能（登录、人口列表、标签筛选、统计）。
