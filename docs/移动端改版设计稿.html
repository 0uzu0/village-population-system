界 面 设 计 稿 · 待 评 审

掌上村务 · 移动端 v4

这一版不改功能、不改接口、不改权限，只改一屏之内先看见什么。 移动端的用户是站在院子里、一只手拿着手机、屏幕还反着光的网格员—— 设计要做的不是让他多看几个字，而是让他在三秒内拿到那个能直接说出口的数字。

版本 v4 设计稿 日期 2026-10-21 屏幕 9 屏（含深色档） 尺寸 360 × 740 dp · 1:1

01设计判断

评审要看的是「为什么这么改」，所以先把观察到的事实摆出来。下面四条都来自现有代码与真实使用场景， 不是审美偏好；每条后面跟的决策，是这一版真正动刀的地方。

观察一：报数的人，第一眼拿不到那个数

工作台首屏依次是：问候 → 三行口径说明 → 两片快捷瓦片 → 四张等大数字卡。 四张卡里只有「总人口」是开会上要说的，另外三个是参照数，却和它一样大。 一屏 656dp 的可用高度，被口径说明（76dp）和等大卡（238dp）用掉了将近一半。

决策 M1　把在册人口做成 40sp 的主数字，另三个降为一行内的参照值。 M2　口径说明默认收成一行，点开才展开——它第三次之后就是噪音，但不能删。

观察二：同一句话说了两遍，还是小字

「重点人群」九行里，老年人与未成年人各挂一行「按年龄自动判定，无需打标签」， 同样的意思占掉 30dp 并且打断竖向扫读；而它们和「低保对象」这种真标签在视觉上完全没有区分。

决策 M3　年龄类族群改用空心圆点 + 行内「按年龄」小胶囊， 身份类用实心色点。行高 44 → 40dp。区别从「多读一行字」变成「一眼看形状」。

观察三：详情页三屏长，但电话是半行字

人员详情七张卡平铺（基本信息 / 户籍居住 / 家庭 / 服务台账 / 残疾档案 / 备注 / 变更记录）， 整页约 1950dp，接近三屏。走访时真正高频的两件事——给人打电话、给他拍照—— 一个是一行 30dp 高的可点文字，一个是第三张卡里的 TextButton。

决策 M4　头像卡下直接给两枚 44dp 动作按钮（拨打 / 拍照）； 服务台账、变更记录改为默认收起的低频分组。

观察四：拍照页的「空框」不会说话

拍照页的空态是一个灰底长方形 + 一枚小图标 + 一行「拍照或从相册选择」， 真正的按钮在它下面 60dp。用户在户外站着一只手操作，先要读完、再找到按钮、再点。

决策 M5　把空框本身做成快门：虚线画幅 + 中心相机圆牌 +「点这里拍照」， 整块可点；从相册选退成画幅下的一行小字。少一次定位。

这一版不做的事，同样是设计决策：不引入新的品牌色，不动已有的蓝 / 墨 / 绿 / 琥珀体系； 不改四格数字背后的统计口径；不新增页面；不为了「好看」缩小正文字号—— 现场是晒谷场和正午的强光，17sp 正文、50dp 主按钮、44dp 触摸目标是硬底线。

02设计语言

沿用现有令牌（AppTokens / AppShapes / AppTypography）， 这一版只新增一个「主数字」字号档与两个间距档，其余不动——设计稿与代码之间已经有 AppTokensTest 在逐值比对，能不改就不改。

颜色

括号内是压在该色实际底色上的对比度，全部经 AppTokensTest 断言 ≥ 4.5:1（WCAG AA）。 三个语义色今年校订过一次：原来的「点缀色」当文字用只有 3.3～4.2:1，在高亮处反而看不清。

动效

页面切换 0 ms

瞬时切换不是省事：淡入淡出期间新旧两屏同时在组合树里，手指会穿透到上一屏的行上（已实际发生过误入详情）。

骨架 850 ms 呼吸

形状与真实行一致，数据到达时整页不重排。系统关掉动画时给稳定中间值，不闪。

按钮涟漪 10% 墨

列表与筛选片不给涟漪；按钮必须有——点「保存」后要等一个网络来回，没反馈就会再点一次。

04三处改版的前后对照

只列动过结构的屏。数字是实际布局尺寸（dp），可以拿去和实现后的截图对账。

1 · 工作台：一屏之内换主角

现在四张等大数字卡
  • 头 44 + 间距 12 + 口径说明 76 + 12 + 瓦片 58 + 12 + 概况卡 238
  • 进入族群区已用掉 464dp，656dp 的视口只剩 192dp：看到 3 行
  • 「按年龄自动判定」重复出现 2 次，各占 15dp
  • 待核查是一张和别的卡一样重的白卡，排在第 5 位
改后一个主数字 + 一行参照值
  • 头 40 + 12 + 主数字卡 160 + 12 + 瓦片 56 + 12 + 待办条 44 + 12
  • 进入族群区用掉 348dp，剩 308dp：看到 6 行，且多出待办条
  • 口径收成一行（30dp），展开时仍然是完整原文
  • 净收益：首屏多 3 行族群 + 一个大数字 + 一条待办，前四块少用 116dp

2 · 人员详情：先能打电话，再看档案

现在七张卡平铺 ≈ 1950dp
  • 拨打 = 一行 30dp 的蓝色文字（InfoRow 的 onValueClick）
  • 拍照 = 照片卡里的 TextButton，触摸高 40dp
  • 服务台账 / 残疾档案 / 变更记录与基本信息同权重，合计约 660dp
  • 「编辑」在页头右上角，视觉上比「重试」还轻
改后名片 + 动作 + 折叠 ≈ 1290dp
  • 拨打 / 拍照 = 名片下 44dp 一对按钮（实底 + 描边），触摸目标达标
  • 低频三组折叠，标题里写明内含字段；展开是同一批 InfoRows
  • 「编辑」改为页底 50dp 主按钮
  • 净收益：少滚 660dp（约 1 屏），高频动作全部在首屏

3 · 拍照留痕：空框即快门

现在空框 + 框下按钮
  • 灰底 104dp 空框里只有图标与「拍照或从相册选择」
  • 真按钮在其下 60dp，与空框是两个各自独立的视觉块
  • 空态下主按钮变灰，但没有说明为什么不能按
改后画幅本身可点
  • 196dp 虚线画幅 + 中心相机圆牌 +「点这里拍照」，整块一个点击区
  • 相册入口退成画幅下一行小字（低频动作降级）
  • 禁用按钮写明原因：「请先拍一张照片」

05状态覆盖

设计稿最容易漏的不是「有数据」的那一屏，而是没数据、没网、出错的那些。下面四种状态每一屏都要成立， 本轮一并落到组件里，不再逐屏零散处理。

加载中 · 骨架（与真行同形）
村里网慢，首屏常要一两秒。转圈只说「在等」，骨架说「马上有一列人，长这样」——等的是同一段时间，但页面不像空的。
空 · 说清为什么空，并给一个动作
没有找到匹配的村民
换个关键词试试，或者清空筛选看全部在册人员
清空筛选
「暂无数据」四个字几乎从不解决问题。空态必须回答两件事：为什么空、现在能做什么。没有动作可给时，不摆一颗按不出效果的按钮。
