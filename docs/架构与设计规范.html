01诊断：这次改的不是风格，是六处真实缺陷

做架构整理最怕变成「按个人审美重写一遍」。所以先把已经出问题的地方列出来，规范只针对这些类型。

问题证据后果处理
导出字段两处定义 后端 EXPORT_FIELDS 有「所属村庄」、重点人群标志列、「全部标签」；前端 person/index.vue 的 exportFields 全都没有 功能其实支持，界面却勾不到。用户以为导不出村庄 改为 GET /api/excel/export-fields 下发，前端与 MCP 共用
性别文案五处 person/index、person/detail、keygroup×2、dashboard 各写一遍 === 'MALE' ? '男' : '女' 重点人群页有「未知」，其余页没有；口径无法统一 utils/format.ts 的 genderLabel()
金额格式两处 台账列表页与台账统计页各写一份 ¥ + toLocaleString 改小数位要改两处，漏一处就出现两种写法 formatMoney() 单一实现
菜单与路由两份清单 MainLayout.menus 与 router.children 各写路径/标题/权限；工作台权限就不一致（路由要 dashboard:view，菜单没写） 出现「菜单能点、进去被弹回」的经典错位 router/navigation.ts 单一来源，两边派生
状态列表硬编码 本次新增 MCP 工具参数时又抄了一遍 ['NORMAL','MOVED_IN',…]，被 personStatus.test.ts 当场拦下 新增状态时统计漏改，人员静默消失 改引用 PERSON_STATUSES
键盘避让写两遍 编辑页内容区与吸底条内部各加一次 imePadding() 键盘一弹内容区高度归零，整张表单消失 只在 Scaffold 上做一次（上一版已修）
共同点：六个问题没有一个是「代码写得丑」，全都是同一个概念存在两份实现。所以本次规范的核心不是排版，而是把「单一来源」变成可检查的约束——能写成测试的，就不写成文档。

02五条铁律

① 一个概念，一个来源
状态、标签编码、导出字段、菜单、金额格式、权限码——凡是「两处都要写」的，就必须有一处是派生的。派生不出来的，加一条测试盯着。
② 口径跟着数据走
「仅统计在册」「人群有交叉不可相加」这类话，不能只写在文档里。MCP 工具返回 _meta.caliber，页面用提示条，接口返回 note。
③ 注释写「为什么」
代码已经说明「做了什么」。注释只回答：为什么是这样而不是那样、踩过什么坑、改这里会连带影响谁。
④ 权限只有一套
网页、移动端、MCP 共用同一批权限码与同一个 requirePermission。任何新入口都不许自带账号体系。
⑤ 每个入口都能回去
列表→详情必须带 ?from 并能原路返回；筛选条件写进 URL，刷新与分享不丢现场。

后端的「服务层」边界

src/services/ 只放被多处复用且有口径的读侧逻辑：personQuery（列表筛选与排序白名单）、personTags（标签写入与互斥）、personDisability、importTask。它不持有 HTTP 对象，也不做响应封装。

写操作的事务仍留在路由里——因为事务边界就是「一个接口的一次业务动作」，抽到 service 反而要把 req.user 一起传下去，得不偿失。

前端的四层

页面views/布局、交互、调用 api不写 axios、不硬编码枚举文案

04模块边界：谁负责什么

判断一个文件该不该拆、一段逻辑该放哪，只看一张表：这个模块的「唯一职责」是什么，越界的部分必须搬走。

模块唯一职责对外契约不该出现在这里
auth登录、当前用户、改密/api/auth/*用户增删改（属 user）
person人员档案全生命周期/api/persons/*家庭结构维护（属 family）
family户与成员关系、自动归户/api/families/*人员字段编辑
grid网格与村庄维度、跨网格转移/api/grids/*人员状态变更
tag标签分类与定义、变更流水/api/tags/*给人打标签（属 person）
keygroup重点人群筛选与概览/api/key-groups/*重复定义人群（统一取 focusGroups）
statistics工作台与分布统计/api/statistics/*明细列表
excel导入导出与任务状态/api/excel/*直接改人员表（走 person 的 schema）
pending待核查记录的补录与确认/api/pending/*正式建档（转交 person 逻辑）
ledger专项台账与费用统计/api/ledgers/*人员信息

mcp新增把既有 REST 包装成 AI 工具POST /api/mcp任何业务 SQL、任何新权限
MCP 模块的自我约束：它没有一行 SELECT。所有取数都通过带调用者 token 的 HTTP 转发回到既有模块。这条约束换来三件事——口径不分叉、权限不分叉、审计不分叉。代价是多一跳 loopback（约 2~5ms）。

05注释规范：只写「为什么」

文件头：三句话交代清楚

每个模块开头必须有：职责一句话、关键口径或约束、踩过的坑（如果有）。三句写不出，说明模块职责本身还没想清。

/**
 * 重点人群域：族群概览与多条件下钻。
 *
 * 这两个工具是「AI 最该用」的入口：用户问「有多少低保、多少残疾人」时，
 * 直接查人员表再自己数会漏掉在册口径与互斥标签，必须走这里。
 */

函数注释：写约束，不写步骤

❌ 无信息量✅ 有信息量
// 查询人员列表 // 默认只返回在册人员（NORMAL / MOVED_IN）。要查已迁出、已死亡的历史档案，传 activeOnly=false。
// 保存按钮 // 只在 Scaffold 上做一次 imePadding：加到吸底条内部会被算进「条的高度」，内容区直接归零。
// 转驼峰 // 现状是两套：人员类接口输出驼峰，/grids 与 /pending 返回 SQL 原始行（下划线）。

三种必须写的注释

  1. 口径注释：任何涉及人数、金额、状态过滤的地方，写明「算哪些人、不算哪些人」。例：在册 = NORMAL / MOVED_IN。
  2. 事故注释：修过一个 bug，就把「为什么会这样」留在原处。后来人改这段代码时，才知道哪一行不能动。
  3. 契约注释：对外编码、字段名、路由顺序等「改了会静默出错」的地方，标明这是契约。例：code 是对外契约，不要随意变更。
不要写「TODO：优化」。没有主语、没有条件、没有判据的 TODO，等于给后来人留了一个无法验证的坑。要写就写清「什么情况下需要优化、优化到什么指标」。

06导航与跳转：只有一条主干

三层结构

层入口去向返回方式
一级侧边栏（由 NAV_ITEMS 派生）各业务列表页—
二级列表行点击、行内「详情」人员详情 /persons/:id?from=…详情页返回按钮回到 from，筛选条件不丢
三级页内弹窗 / 抽屉编辑、标签、状态变更关闭即回原列表，不跳页

三条硬约束

  • 不新增孤立页面。任何页面至少要有一个入口，且入口在主干上。只靠手输 URL 能到的页面，等于不存在。
  • 跨页跳转必须带上下文。用 utils/nav.ts 的 toPersonDetail(route, id) 带上 ?from；列表页用 useListUrlSync 把筛选写进 URL。
  • 不重复实现同一个功能入口。同一个人可以从人口档案、重点人群、家庭、网格四个地方被看到，但这四个入口都跳到同一个详情页，不允许各自实现一套「查看」。

导航单一来源（本次落地）

改之前：菜单与路由各写一份 path / title / perm，而且工作台权限已经不一致。改之后：

router/navigation.ts      定义一次 NAV_ITEMS（path / title / icon / perm / component）
        ├── router/index.ts    → children 与 meta（守卫读 meta.perm）
        └── layouts/MainLayout → 侧边栏渲染与权限过滤

收益不只是少写几行：权限判断从此只有一处输入。菜单可见性、路由拦截、面包屑标题全部同源，不可能再出现「能点但进不去」。

08设计风格：用令牌，不用数值

三份样式文件的分工

文件管什么规则
styles/tokens.css颜色、字号、间距、圆角、阴影页面里只能引用变量，不写 #3978F6、14px
styles/element-override.cssElement Plus 组件的统一外观覆盖集中在这里，页面不写 :deep(.el-table th)
styles/base.css重置、滚动条、通用工具类不含业务样式

列表页的统一骨架

14 个页面里 9 个是「筛选 + 表格 + 分页」。它们的结构必须一致，用户不需要在每个页面重新学一遍：

┌ 页头 ──── 标题 + 主要动作（新建 / 导入 / 导出）
├ 筛选区 ── 常用条件一行，高级条件可折叠；「查询 / 重置」固定在右端
├ 表格 ──── 2~3 列 min-width 弹性；操作列固定右侧；空态用统一文案
└ 分页 ──── 右对齐；切换每页条数不重置筛选

四条视觉约束

  • 字号只用语义令牌（--fs-title / --fs-body / --fs-caption），不写 px。移动端踩过同样的坑，两端口径一致。
  • 主色只用于可点击与选中。状态色（成功/警告/危险）不得借用主色，否则用户分不清「能点」和「已完成」。
  • 空态与错态分开：空态说「还没有数据，怎么添加」；错态说「为什么失败，怎么重试」。统一走 EmptyBox / ErrorBox 的骨架。
  • 表格里的空值写「未登记」而不是「—」。「—」会被读成「不适用」，而实际是「没填」。

09MCP 接入层（新增）

目标：让 AI 客户端在权限边界内直接查人口、家庭、网格、标签、重点人群、台账与统计。不新开一套数据通道，只给既有 REST 加一层「AI 友好外壳」。

为什么复用 REST，而不是直连数据库

方案做法问题结论
A 直连库MCP 自己写 SQL在册口径、互斥标签、残疾等级、家庭在册判定分散在路由 SQL 里，复制必漂移；且绕过 RBAC 与审计否决
B 抽服务层查询下沉，REST 与 MCP 共用13 个模块全量重构，回归面覆盖整个系统M3 再演进
C 复用 REST带调用者 token 请求本机接口多 2~5ms；需归一化字段风格采用

四个设计决定

无状态 Streamable HTTP
不维护 session，容器可随时重启；响应用 JSON 而非 SSE，nginx 不必关 buffering，也便于 curl 排障。
工具清单按权限过滤
没权限的工具直接从 tools/list 消失，而不是列出来再返 403。模型不会去试一个注定失败的调用。
默认脱敏
身份证保留前 6 后 4，手机号前 3 后 4，银行账号只留后 4。要明文须部署方显式设 MCP_PII_MODE=full。
写操作三级开关
MCP_WRITE_LEVEL=off|basic|full 控制读写；删除类（danger）还需要额外的 MCP_ALLOW_DESTRUCTIVE=true。

协议要点

项取值说明
协议版本2025-03-26Streamable HTTP 正式版；不支持批量请求
方法initialize / tools/list / tools/call / ping通知（notifications/initialized）返回 202 无响应体
错误分层协议错误 vs isError参数/方法错 → JSON-RPC error；业务错（403/404）→ isError 内容 + 下一步提示
审计mcp.<tool>落 audit_log，含工具参数、真实 IP、耗时；内部转发请求不重复记账
限流120 次/分·账号按账号而非 IP：全村共用一个出口 IP

字段归一化与口径下发

现有接口一半驼峰（personNo）、一半下划线（grid_no）。MCP 出口统一转驼峰，并在 _meta 里带上口径：

  "items": [...],
  "total": 1204,
  "page": 1,
  "hasMore": true,

    "tool": "person_search",
    "durationMs": 42,
    "caliber": "默认只返回在册人员（NORMAL / MOVED_IN）……"
  }
}

11扩展指南：加东西只改一处

加一个 MCP 工具（5 步，约 20 行）

// 1. 在 src/modules/mcp/tools/<域>.ts 里追加一个 ToolDef
{
  name: 'ledger_delete',               // snake_case，发布后不可改名
  title: '删除台账记录',
  description: '删除一条台账记录。会连带解绑附件，不可恢复。',
  domain: 'ledger',
  scope: 'danger',                     // read | write | danger
  permission: 'ledger:manage',         // 与 REST 同一个权限码
  params: [
    { key: 'id', type: 'integer', desc: '台账记录 id', required: true, min: 1 },
  ],
  async exec(ctx, args) {
    // 复用既有接口：DELETE /api/ledgers/records/:id
    return shape(await ctx.send('DELETE', `/ledgers/records/${args.id}`));
  },
}

// 2. 无需改注册表（tools/<域>.ts 的数组已被 registry 汇总）
// 3. 无需改协议层、鉴权、脱敏、审计
// 4. 跑 backend/test/mcp.test.ts（校验命名/权限/描述长度）
// 5. danger 工具默认不注册：需 MCP_WRITE_LEVEL=full 且 MCP_ALLOW_DESTRUCTIVE=true

加一个页面

  1. 在 router/navigation.ts 的 NAV_ITEMS 追加一项（path/title/icon/perm/component）。
  2. 菜单、路由、面包屑、权限拦截自动生效，不需要再去 MainLayout 改一遍。
  3. 列表类页面套用 useListUrlSync + useColumnVisibility，不要手写分页与 URL 同步。

加一个后端接口

  1. 放进已有模块；只有「确实属于新业务域」才新建 module，并在 app.ts 挂载。
  2. 统一 ok() / okPage() / AppError，不自己拼响应体。
  3. 写操作必须 withTransaction + writeAudit；涉及人员统计的查询必须带 activeSql。
  4. 前端 api/index.ts 加一行；apiRouteCoverage.test.ts 会校验路径存在。

加一类重点人群

只改 utils/focusGroups.ts：工作台卡片、快捷入口、网格/村庄统计列、导出标志列全部由它派生。改完跑 quickGroups.test.ts。
